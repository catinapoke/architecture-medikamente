# Задание

Компания планирует миграцию существующей информационной системы на новую платформу. В качестве подхода студент должен выбрать один из трёх вариантов миграции и на его основе разработать детальный cutover план.

1. **High-level design.** Применение широких архитектурных принципов: проектирование с учётом домена, определение модульных границ.
2. **Parallel run.** Запуск старой и новой системы параллельно для постепенного перевода нагрузки.
3. **Branch by abstraction.** Постепенный перенос функциональности слой за слоем с использованием абстракций.

## Что нужно сделать

1. **Проанализировать текущую ситуацию и выбор стратегии.**
  - Изучить описание существующей системы, требования к новой архитектуре и бизнес-цели миграции.
    - Обосновать выбор одного из трёх вариантов миграции, указав его преимущества и ограничения для конкретного сценария.
2. **Разработать cutover-план.**
  - Составить поэтапный план миграции для выбранного варианта с описанием всех этапов: подготовки, тестирования, реализации, мониторинга, плана отката.
    - Определить критические моменты и меры по минимизации рисков.
3. **Выявить риски и распределить роли.**
  - Выявить ключевые риски, связанные с выбранной стратегией. Например, для Parallel run — синхронизация данных, для Branch by abstraction — согласованность версий.
    - Разработать план действий на случай возникновения проблем и распределить роли между участниками процесса.
4. **Сформировать отчёт.**
  Представить документ с cutover-планом в виде таблицы или блок-схемы. Обязательно дополнить пояснительным текстом, в котором описаны этапы миграции, обоснование выбранного подхода, мероприятия по управлению рисками и распределение ответственности.

# Решение



## Проанализировать текущую ситуацию и выбор стратегии

Сейчас у медицинского центра вся работа построена на ручной работе с Excel файлами и сканами документов. Дополнительно есть 1С и ККМ. 

Планируется переход к уменьшению ручной работы: порталу для сотрудников и клиентов, платежный шлюз и др. 

Excel файлы раздельны на каждый процесс:

- Запись
- Регистрация
- Просмотр и заполнение мед. данных

High-level design, если я правильно понял идею урока, предполагает переход через "большой взрыв" и выглядит довольно рисково, поскольку не дает возможности откатиться на рабочую версию и продолжить работу центра независимо. Также такой подход требует сразу больших временных вложений. 

Parallel run предполагает внесение изменений в обе системы, что увеличит объем работы на время перехода и поставит задачу проверки расхождений сразу во всех областях. При проблемах потребуется синхронизация в обе стороны. 

Branch by abstraction - при переносе работы системы по частям можем столкнуться с проблемой согласованности данных: в старой системе есть данные, а в новой нет, или они другие и наоборот. Excel под API не прячем: файлы так не работают, сотрудники всё равно откроют `.xlsx`. Вместо этого слой абстракции — портал сотрудников, который наращиваем модулями и ими же вытесняем отдельные Excel.

Выбор подхода: High-level design сразу отсекаем так как в нем больше всего рисков. Далее между Parallel run и Branch by abstraction скорее стоит выбрать branch by abstraction поскольку сейчас уже есть риск с согласованностью данных и он должен в какой то степени решаться, когда при parallel run нужно продумать и реализовать синхронизацию в обе стороны и делать двойную работу. Начинаем с малого объёма пациентов, чтобы при откате не возвращать в Excel сразу весь журнал. 

## План перехода с ролями

Начинаем работу с портала сотрудников: каждый новый модуль закрывает свой процесс и вытесняет свой Excel. 

Порядок модулей: 

1. авторизация сотрудников
2. регистрация пациентов
3. записи к врачам
4. мед. данные
5. интеграция партнёра по анализам

Мониторинг включаем после авторизации сотрудников, чтобы понимать, выдерживает система нагрузку или нет.

Портал пациентов включаем после этого, когда контур сотрудников уже работает. 

Платёжный шлюз можно вести параллельно: он слабо зависит от ресепшена и врачей, но 1С нужно перевести на веб-сервер до шлюза. 

Каждую волну начинаем с малого объёма пациентов, чтобы откат не возвращал в Excel сразу большой журнал.
